# recsys-rl-finetuning

RL-дообучение последовательной рекомендательной модели (GPT-2) на KION (МТС): reward model по доле просмотра, GRPO с KL-штрафом к базовой модели и разбор того, что происходит с рекомендациями. Задача T-Lab №2.

Всё исследование находится в одном ноутбуке [solution.ipynb](solution.ipynb) (выполнен на Kaggle, T4, 85 минут, выводы ячеек сохранены). Лёгкие результаты лежат в [results/](results/).

## Коротко

- Базовая GPT-2 лучше сильного бейзлайна «популярное за 7 дней»: Recall@10 0.212 против 0.196 на val (разность +0.017 [+0.014, +0.020]).
- Reward model с известными откликами предсказывает долю просмотра с AUC 0.745 (среднее по объекту: 0.672).
- RL легко повышает reward, но платит релевантностью. Единственная настройка без заметной потери — сильный KL (β=8): Recall@10 −0.001, reward +0.028. При β=0.5 reward растёт на +0.163, Recall@10 падает с 0.212 до 0.142, модель рекомендует всем короткие хиты (длительность 391 → 156 мин, покрытие 0.243 → 0.082).
- Награда «вернулся в течение 3 дней» приводит к эксплуатации: Recall@10 0.009, всем рекомендуются около 10 фильмов серии Marvel.
- Цепочка из 5 собственных рекомендаций теряет вдвое в релевантности к 5-му шагу (Recall@10 0.152 → 0.072), а при реальном продолжении нет (0.167).

## Данные и протокол

KION: 5.48 млн взаимодействий, 962 тыс. пользователей, 15.7 тыс. объектов, 2021-03-13 … 2021-08-22. Отклик — `watched_pct`. После фильтра (≥5 событий в train) остаётся 240 тыс. пользователей и 14.9 тыс. объектов.

- **Разбиение строго по времени:** train до 2021-08-02, val 08-02…08-08, test 08-09…08-22. Словарь объектов — только из train. Для test контекст — всё, что было до начала test (train + val). Проверки на утечки встроены в ноутбук.
- **Eval-кейс:** пользователь, цель — его первое событие в периоде, контекст — последние 50 событий до периода. Val 58 173 кейса, test 74 148.
- **Одинаковый протокол** для бейзлайнов, базовой и RL-моделей: ранжируется весь каталог без уже просмотренного. Метрики Recall@K (= HitRate), NDCG@K, MAP@K (= MRR@K), покрытие, Gini, популярность. Доверительные интервалы 95% — бутстреп по пользователям (1000 повторов), разности — парный бутстреп.
- Test открывался один раз в конце, ничего по нему не подбиралось.

## Модели

- **База:** GPT-2 с нуля (4 слоя, 256, 7.0 млн параметров), next item prediction, окна по 50 объектов, 6 эпох.
- **Reward model (RM-A):** каузальный GPT-2 над объектами и прошлыми откликами пользователя, голова предсказывает `watched_pct` кандидата. У 50% окон при обучении отклики скрыты, чтобы RM работала и на сгенерированных последовательностях.
- **RL:** GRPO (REINFORCE с групповым baseline) + точный KL(π‖π_ref) по всему каталогу. 250 шагов, lr 3e-5, 128 контекстов × 8 траекторий на шаг. Просмотренное маскируется.
- **Награды:** `pct` (RM-A), `pct+hit` (+0.5 за совпадение с реальным следующим объектом), `pct+div` (штраф η·ln c за скопление одного объекта в батче, η = 0.01 и 0.05), `long` (RM-ret, вероятность вернуться за 3 дня), `pct+long`. Сетка β = 0.1, 0.5, 2, 8 для `pct`, остальные при β=0.5 (`long` ещё и при 0.1). Вариант `pct_H5` — горизонт 5 шагов.
- **Дополнительно:** RM-B (1 слой, другой seed) как независимая проверка, RM-ret для долгосрочной цели.

### Как изменилось поведение и почему

- **Короткие хиты.** Длительность топ-10 падает с 391 до 156 мин (β=0.5), доля сериалов с 0.30 до 0.09, средний досмотр рекомендованных объектов в train с 51% до 68%. RM в основном выучила эффект объекта (среднее по объекту уже даёт AUC 0.672), поэтому политика находит объекты с высокой долей досмотра.
- **Потеря персонализации.** При β=0.5 покрытие 0.082, 97% слотов приходится на 100 объектов (у базы 73%). Потеря Recall одинакова по группам: относительно базы −31% / −34% / −38% для истории 5–9 / 10–24 / ≥25 и −32% / −35% / −33% по вовлечённости.
- **Схлопывание при слабом KL.** При β=0.1 энтропия политики 0.06, около 220 объектов на весь каталог. Reward в топ-10 при этом ниже, чем при β=0.5 (0.623 против 0.673): оптимизируется только первый объект.
- **Это не только ошибки RM.** Фактический средний досмотр рекомендованных объектов по данным val (RM его не использовала) растёт с 46.7% до 59.5%. RM-B повторяет RM-A (корреляция предсказаний 0.985), поэтому как независимый судья она не годится.

### Долгосрочная цель

Целевой сигнал: пользователь вернулся (новое событие в другой день) в течение 3 дней; в данных нет лайков и сессий, только даты. RM-ret предсказывает возврат с AUC 0.684 [0.679, 0.689]; среднее по пользователю даёт 0.649, среднее по объекту 0.567. Объект влияет на возврат слабее, чем пользователь, а возврат тяжёлого пользователя не причинное следствие рекомендации.

Оптимизация по этой награде эксплуатирует именно это: Recall@10 падает до 0.052 (β=0.5) и 0.009 (β=0.1), при β=0.1 каждому рекомендуются те же около 10 фильмов Marvel (по 9.8% слотов), хотя фактический возврат этих объектов в val высок (0.72 против 0.52 у базы). Это эффект отбора (их смотрят активные пользователи), а не доказанное влияние на возврат.

Офлайн проверяются релевантность, поведение, reward по RM и фактические исходы по логам. Причинный эффект на возврат и удовлетворённость требует онлайн-эксперимента (A/B) или офлайн-оценки по пропенсити логирующей политики, которых в KION нет.

## Ограничения

- Один запуск на конфигурацию (seed 0); доверительные интервалы по пользователям, разброс RL между seed не измерен.
- Релевантность по одному следующему объекту (Recall@K = HitRate); для рекомендованных, но не просмотренных объектов исход неизвестен.
- В KION нет времени внутри дня, лайков и длительности объектов (длительность оценена по `total_dur` и доле досмотра).
- RM-B почти копия RM-A, независимой награды нет; фактический досмотр — среднее по объекту, не персональный исход.
- Повторных просмотров в данных нет, повторные рекомендации не исследованы.
- Многошаговая оценка сделана на пользователях с ≥5 событиями в периоде (смещение к активным).
- Всё офлайн, влияние на реальное поведение не измерялось.

## Направления дальнейшей работы

- Промежуточные β между 2 и 8, где проходит граница допустимой потери.
- Ограниченная оптимизация: максимум reward при Recall ≥ база − ε (множитель Лагранжа вместо фиксированного β), бонус за энтропию против схлопывания.
- Несколько seed и ДИ по запускам.
- Причинная оценка долгосрочной награды (онлайн A/B или офлайн-оценка по пропенсити).
- RM, обученная на контекстах из сгенерированных объектов.

## Воспроизведение

Ноутбук рассчитан на Kaggle (GPU T4 или P100): режим выбирается автоматически (на Kaggle полный прогон, локально малая выборка на CPU).

1. Загрузить `interactions.csv`, `items.csv`, `users.csv` (KION) как приватный Kaggle Dataset.
2. Создать ноутбук, импортировать `solution.ipynb`, подключить датасет, включить GPU.
3. **Save Version → Save & Run All (Commit)**: полный запуск занимает около 85 минут, окно браузера держать открытым не нужно.
4. Лёгкие результаты (`results/*.json`, `*.csv`, `*.png`) скачиваются из Output версии. Тяжёлые чекпойнты и кэш (`checkpoints/`, `cache/`) в репозиторий не входят.

Локально (`pip install -r requirements.txt`, путь к данным в переменной `DATA_DIR`, см. `.env.example`) ноутбук работает на малой выборке 30 тыс. пользователей и нужен для проверки кода; полный прогон на CPU не рассчитан.
